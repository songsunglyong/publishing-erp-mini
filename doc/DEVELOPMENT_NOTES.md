# 개발 과정과 검증 근거

이 문서는 기능 개수보다 설계 이유·실패 원인·검증 방법을 보여 주기 위한 기록이다. 학습·포트폴리오에서 실제 수행한 작업을 정리하며, 실제 고객 장애·운영 트래픽·개인이 전부 직접 작성한 실적으로 바꾸어 표현하지 않는다.

## 1. 화면 동작에서 데이터 정합성으로

처음에는 도서·거래처 등록/조회/수정/비활성화부터 요청→Controller→Service→MyBatis→DB→JSP 흐름을 연결했다. 신규 도서는 재고 0행까지 같은 트랜잭션에서 생성하고, 비활성화는 과거 관계를 보존하도록 UPDATE로 처리했다. 검색은 파라미터 바인딩·와일드카드 이스케이프·전체 개수와 페이지 조회를 구분했다.

근거: [구조 안내](PROJECT_WALKTHROUGH.md), [ERD](erd.md), MasterDataTest.

## 2. 출고 중 일부 품목만 저장되는 문제를 실험

합성 데이터·임시 소스 사본·별도 테스트 DB에서 품목마다 REQUIRES_NEW로 커밋하는 오류를 의도적으로 만들었다. 첫 도서 5권 중 2권이 차감된 뒤 두 번째 도서 재고 부족이 발생했을 때, 기대 5권/실제 3권으로 회귀 테스트가 실패했다.

원장 처리를 주문의 트랜잭션에 참여하도록 MANDATORY로 복구하고 같은 테스트가 통과함을 확인했다. ‘트랜잭션이 있다’는 것과 ‘하나의 업무를 같은 트랜잭션으로 묶었다’는 차이를 검증한 사례다. 실제 고객 장애를 해결한 이력은 아니다.

근거: [실패→성공 재현 기록](maintenance-case.md), TransactionTest.

## 3. 동시에 들어오는 요청과 과거 거래 보존

주문·재고 행 잠금과 도서 id 순서, 주문 상태 검사·DB UNIQUE 처리 키를 조합했다. 동시 출고·중복 출고·동시 반품을 실제 MariaDB 연결로 검증했다. 주문 당시 단가/명칭을 저장해 이후 정가 변경이 과거 거래와 반품액을 바꾸지 않게 했다. 반품의 원주문 품목 소속·잔여 수량 검사와 월을 넘긴 반품 집계도 확인했다.

근거: [업무별 학습 설명](PHASE2_4.md), [구조/집계 정의](architecture.md), TransactionTest.

## 4. 보안은 버튼 숨김과 검사 성공 표시만으로 판단하지 않음

URL/Service 역할 검사·직원 객체 접근·CSRF·세션 만료/교체·계정 폐기와 로그 비노출을 테스트했다. 실제 JSP HTTP 출력으로 script/img 입력 이스케이프도 확인했다. 추가 SQL Injection 회귀는 공격 구문이 실제 MariaDB에서 조회 조건이 아닌 문자열로 처리되는지 검사한다.

초기 CI 취약점 단계가 성공했지만 Java 분석 대상이 0개인 문제를 발견해, WAR 분석과 필수 라이브러리 포함 여부 검사로 보완했다. 패키지 수·심각도 범위를 실제 확인하며 취약점 무시 목록으로 통과시키지 않았다. 자동 검사 성공이 모든 보안 결함의 부재를 뜻하지 않는다는 한계도 기록했다.

근거: [보안 점검](SECURITY_AUDIT_2026-10-31.md), [CI/릴리스 기록](RELEASE.md), .github/workflows/security.yml.

## 5. 프레임워크와 Java 패치도 회귀 확인

사용자 승인으로 Boot 4/MyBatis Starter 4/Security 7/Jackson 3을 호환 조합으로 전환했다. 기존 업무 SQL은 유지하면서 스타터·설정 키·테스트 import를 조정하고 실제 WAR/JSP·전체 회귀·원격 보안 검사를 수행했다.

이후 JDK 인증서 신뢰 문제를 확인해 프로젝트 전용 Temurin 21.0.13+9 ARM64를 설치했다. 공개 테스트 체인 16개는 기존 JDK에서 허용/새 JDK에서 거부됐고 정상 HTTPS도 확인했다. 새 JDK에서 전체 93개/WAR를 검증했다. 설치만으로 다른 서버/컨테이너/IDE까지 바뀐다고 주장하지 않는다.

근거: [Boot 4 전환](BOOT4_MIGRATION.md), [Java 패치](JAVA_PATCH.md), [테스트 결과](TEST_RESULTS.md).

## 6. 구현과 운영 설계를 구분

Docker 산출물·베이스 이미지 검사는 있지만 완성 앱 컨테이너 운영·HTTPS 호스팅·백업 복원은 아직 검증하지 않았다. 점검 HTML·제한된 운영 확인·두 앱 전환·공유 세션·DB 호환 롤백은 설계 단계다. B2C는 별도 쇼핑몰이 ERP id를 전달하는 주문 수신 규격으로 책임을 제한했다.

근거: [운영 설계](OPERATIONS_DESIGN.md), [쇼핑몰 주문 설계](MALL_ORDER_DESIGN.md).

## 개발 방식과 설명 범위

PHP 웹·Android/iOS 유지보수 경험에서 Java/Spring으로 전환하는 학습 프로젝트이며 AI 개발 보조를 사용했다. 요구사항·설계 선택·테스트와 실제 수정 과제를 연결하고, 이해하지 못한 부분은 다시 설명·수정하는 방식으로 진행했다. 구현 완료와 개발자의 이해 완료는 LEARNING.md에서 구분한다. 직접 담당한 기존 유지보수 사례·기간·성과는 확인된 사실만 지원서에 추가한다.

현재 저장소는 사용자 결정에 따라 비공개다. 향후 공개 전 비밀정보/개인정보·로그·이미지·예시 데이터·접근 권한을 다시 점검한다. 이 문서는 공개 전환을 실행하거나 비밀정보가 영구히 없음을 보장하는 문서가 아니다.
