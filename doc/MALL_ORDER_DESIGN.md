# 쇼핑몰 주문 수신 설계

작성일: 2026-11-01. **설계 채택, API·테이블·화면은 미구현**이다. 쇼핑몰 자체를 ERP 안에 개발하지 않는다. 현재 검증된 B2B 기능과 향후 확장 범위를 구분한다.

## 1. 책임과 도서 식별자

쇼핑몰은 상품 판매·고객 화면·결제 처리를 담당하고 ERP는 정해진 양식의 주문을 받아 검증·저장한 뒤 직원이 확정·출고·반품을 처리한다. 양식은 전달 필드의 규격이며 이 설계에서는 서버 간 주문 수신 API를 목표로 한다. 엑셀 업로드나 쇼핑몰 화면까지 구현했다는 뜻은 아니다.

**ERP가 발급한 books.id를 공통 도서 식별자로 사용한다.** 기존 id는 BIGINT PK이고 현재 수정 SQL은 이 값을 바꾸지 않는다. 비활성화도 행을 삭제하지 않는다. 이번 단일 ERP 연동에서는 별도 book_code를 의무적으로 추가하지 않는다. 앞서 별도 코드가 필요하다고 제안한 안보다 사용자가 제안한 기존 키 재사용을 우선한다.

```text
ERP books.id=25 발급 → 쇼핑몰 상품에 erp_book_id=25 매핑
쇼핑몰 상품번호는 자체 관리 → 주문 품목에는 ERP가 발급한 id 전달
ERP가 25번 도서의 존재·사용 상태·수량·단가를 검증
```

주의 조건:

- ERP id를 쇼핑몰에서 새로 생성하거나 제목/ISBN으로 추정하지 않는다. 재고가 생긴 도서의 id를 변경·재사용하지 않는다.
- id는 **그 ERP 데이터 집합 안에서 고유**하다. 운영 25번과 개발 DB 25번은 다른 책일 수 있다. 쇼핑몰은 자신이 연결된 운영 ERP의 id를 사용한다.
- DB 이관/복원에서는 기존 키와 관계를 보존한다. 초기화/재등록으로 번호가 바뀌면 재매핑이 필요하다. DB/ERP 여러 개를 합치거나 외부 시스템이 늘어나면 외부 코드/매핑 테이블을 다시 검토한다.
- 연속된 숫자를 아는 것은 권한을 뜻하지 않는다. 인증과 데이터 접근 검사는 별도다.
- JSON의 BIGINT 정밀도 문제를 피하기 위해 외부 규격의 erp_book_id는 십진수 **문자열**로 정한다. ERP에서 양수 Long 범위로 엄격히 변환한다. 내부 book_id는 기존 BIGINT를 유지한다.

## 2. 업무 흐름

```mermaid
flowchart LR
    B[ERP 도서 id 발급] --> M[쇼핑몰 상품에 매핑]
    M --> S[쇼핑몰 주문 접수]
    S --> A[인증된 서버 간 주문 수신]
    A --> V[양식·도서·수량·단가·중복 검사]
    V --> D[ERP DRAFT 주문 저장]
    D --> C[직원 확인·확정]
    C --> F[출고·재고 차감·원장]
    F --> H[직원 배송정보 기록]
```

주문 수신만으로 재고를 예약/차감하거나 매출로 계산하지 않는다. 현재 확정 비예약·출고 차감 규칙을 유지한다. 외부 결제 완료는 ERP 출고 완료와 다른 사건이다. 결제 API·카드 정보·고객 비밀번호는 ERP로 받지 않는다.

## 3. 최소 주문 양식 v1

아래는 실제 개인정보가 없는 **합성 예시**이며 현재 동작하는 요청 주소가 있는 것은 아니다.

```json
{
  "schema_version": 1,
  "external_order_no": "DEMO-20261101-0001",
  "ordered_at": "2026-11-01T09:00:00+09:00",
  "recipient": {
    "name": "시연 수령인",
    "phone": "010-0000-0000",
    "postal_code": "00000",
    "address1": "시연용 주소",
    "address2": "시연용 상세 주소",
    "delivery_note": "시연용 요청사항"
  },
  "items": [
    {"erp_book_id": "25", "quantity": 2, "unit_price": 18000}
  ]
}
```

필수 검증: 지원 schema_version, 외부 주문번호 길이/형식, 시간대 포함 주문일시, 수령인/주소 길이·필수값, 1~20품목, 존재하는 사용 도서, 양수 수량, 기존 금액 한도. 같은 도서가 두 줄에 중복되면 거부한다. 외부 번호는 trim 후 빈 값/허용하지 않은 공백을 거부하고 대소문자 구분 정책을 DB 제약과 맞춘다.

쇼핑몰은 채널별 판매 단가가 다를 수 있으므로 정가와 무조건 같다고 요구하지 않는다. 허용 범위/계약을 검사하고 서버가 수량×단가·총액을 계산한다. 외부의 총액·직원 번호·ERP 상태·채널·거래처 FK를 그대로 믿지 않는다. 할인/배송비/쿠폰/세금은 v1 범위 밖이며 모르는 금액을 조용히 무시하거나 상품 대금에 섞지 않는다. 별도 합의 없이 자동 반영하지 않는다.

## 4. 중복 수신과 변경 요청

쇼핑몰 식별자는 인증된 자격에서 결정한다. 요청 본문의 mall_code를 믿어 다른 쇼핑몰 주문을 등록/조회하게 하지 않는다.

- 중복 기준: **(mall_client_id, external_order_no)** UNIQUE. 현재 일반 주문의 UUID request_key와 목적이 같더라도 외부 주문의 업무 식별은 별도로 유지한다.
- 동일 번호·동일 정규화 내용의 재전송: 같은 ERP 주문 id를 돌려주고 추가 저장하지 않는다. DB UNIQUE로 동시 수신도 방어한다.
- 동일 번호·다른 내용: 충돌로 거부한다. 재전송을 주문 수정으로 해석하지 않는다. 내용 비교는 수령 정보·주문일·정렬한 품목 등을 포함한 표준 정규화 digest를 이용하고 원문을 로그에 쓰지 않는다.
- 주문 변경/취소/반품 동기화·ERP→쇼핑몰 배송 통지는 후속 별도 규격이다. 수신 v1에 자동 포함하지 않는다.
- 주문 헤더·품목·배송지·외부 연결은 하나의 트랜잭션으로 저장한다. 한 품목 오류 시 전체를 거부하고 일부 주문을 남기지 않는다.

예정 응답 계약: 신규 201, 동일 재전송 200, 입력 오류 400, 인증 실패 401, 권한 거부 403, 같은 번호의 다른 내용 409, 일시 장애 503. 아직 구현된 응답은 아니다. 성공에는 최소 ERP 주문 id/번호/상태, 실패에는 표준 코드·한국어 안내·추적 ID와 허용된 필드 오류만 준다. 실패 응답에 수령인/주소·토큰·원문 요청을 반사하지 않는다. 타 쇼핑몰의 주문은 조회/중복 응답으로도 노출하지 않는다.

## 5. 기존 데이터 구조와 필요한 확장

현재 sales_orders.partner_id는 NOT NULL이고 created_by는 직원 FK다. 단순히 쇼핑몰 JSON을 기존 Controller에 보내는 것만으로 B2C가 구현되지 않는다. 다음은 **마이그레이션 구현 전 설계**다.

| 대상 | 예정 변경·이유 |
|---|---|
| books | id 재사용, 별도 book_code 필수 추가 없음 |
| mall_clients(신규 예정) | 허용된 쇼핑몰·활성 상태·인증 정보와 ERP 전용 처리 계정 연결 |
| sales_orders | channel=B2B/B2C 추가, 기존 행은 B2B. B2C는 partner_id NULL 허용, B2B는 거래처 필수라는 규칙을 Service/DB에서 검증 |
| 외부 주문 연결(신규 예정) | mall_client_id + external_order_no 유일, ERP sales_order_id 유일, 정규화 digest·외부 주문일 기록 |
| 주문 배송지(신규 예정) | order_id에 주문 당시 수령인/연락처/주소를 보존. 거래처 주소 변경으로 과거 배송지가 바뀌지 않게 함 |
| 배송 기록(신규 예정) | 택배사·송장·배송 상태·처리 시각. v1은 직원 수동 입력·한 주문 한 배송을 기준으로 시작하고 분할배송은 별도 확장 |
| 보고서 | 기존 거래처 보고서에 B2C의 NULL 거래처를 한 곳처럼 섞지 않음. 전체/채널별 요약과 B2B 거래처별 집계 범위를 분리 |

B2C 개인을 가짜 서점 거래처로 등록하지 않는다. 사용자 회원/고객 테이블도 v1에서 반드시 가져오지 않는다. ERP가 필요한 주문별 배송 정보만 받는다. sales_orders.partner_name 같은 기존 스냅샷 필드의 B2C 표시 정책은 쇼핑몰 명칭으로 정의하되 고객 개인을 거래처로 오해하지 않게 하고, 집계는 이름이 아니라 채널/실제 FK로 구분한다.

created_by를 임의 숫자로 채우거나 클라이언트가 넘기는 직원 id를 쓰지 않는다. 현재 CurrentActor는 ErpPrincipal을 요구하므로, 허용된 쇼핑몰에 매핑한 전용 ERP 처리 계정으로 감사·Service 권한 검사를 수행하도록 인증 어댑터를 별도 구현한다. 실제 로그인 직원과 수신 클라이언트도 감사상 구분한다. API 인증에 성공했다고 기존 Service 권한을 우회하지 않는다.

입고 공급처 관리도 별도 후속이다. 거래처의 판매처/공급처 역할과 입고 전표 연결을 설계해야 하며 현재 입고는 도서·수량·사유 기반이다. 이 문서 작성으로 공급처·배송·B2C가 구현 완료된 것은 아니다.

## 6. 보안과 개인정보

- 운영 HTTPS, 쇼핑몰별 서버 자격 증명·폐기/회전·속도 제한. 자격은 브라우저 JS/JSP·예시 JSON·Git에 넣지 않는다. CORS를 열어 인증을 대신하지 않는다.
- 브라우저의 ERP 세션·CSRF는 그대로 유지한다. 서버 간 API는 별도 인증/쿠키 비사용 경계로 한정하고, 필요시 해당 경로만 CSRF 예외를 검토한다. 전체 CSRF를 끄지 않는다. 현재 설정은 변경하지 않았다.
- 도서 id가 유효해도 쇼핑몰 인증/역할과 입력 검증을 거친다. 도서 조회/주문 응답은 해당 쇼핑몰에 허용한 범위로 제한한다.
- 개인정보가 들어 있는 원문 JSON·주소·연락처·토큰을 로그·공개 테스트 자료·추적 ID에 넣지 않는다. 화면 escaping/오류 비노출을 유지한다.
- 배송지 열람 권한·목록 마스킹·DB/백업 접근권한·보유기간/파기 정책을 구현 전에 확정한다. 임의 법정 보유기간을 만들어 안내하지 않는다. 실제 고객 자료 없이 합성 데이터로 검증한다.

## 7. 파일 흐름과 검증 계획

예정 파일 역할: API 인증 계층 → 주문 수신 Controller/입력 DTO → 전용 수신 Service(중복·업무·트랜잭션) → 기존 주문 업무와 Mapper → MariaDB → 최소 JSON 응답. 직원의 주문/출고 화면은 기존 JSP를 확장한다. JSP가 쇼핑몰 요청의 인증·DB 저장을 직접 맡지 않는다.

PHP 비교: 외부 주문 JSON을 받는 PHP 엔드포인트에서 인증→검증→중복 검사→PDO 트랜잭션을 수행하는 흐름과 같다. Java에서는 Controller/Service/MyBatis와 인증 필터에 역할을 나눈다.

미구현 검증 항목:

1. 알려진 id의 정상 주문 수신·DRAFT 저장, 수신만으로 재고/매출 무변경.
2. 미등록/비활성 도서, 잘못된 수량/단가·품목 중복·두 번째 품목 실패 전체 롤백.
3. 동일/동시 재전송 주문 1개, 다른 내용 충돌, 다른 쇼핑몰의 같은 주문번호는 별도 주문.
4. 미인증/차단 클라이언트·위조 mall_code·허용되지 않은 요청 필드 거부, 기존 ERP CSRF/역할 검사 유지.
5. 문자열 id의 Long 범위, 큰 값·형식 오류, 스냅샷 배송지 유지, 개인정보 로그 비노출·JSP escaping.
6. 기존 B2B 주문/출고/반품·보고서 회귀, 채널별 집계, 실제 JSP와 마이그레이션·기존 DB 업그레이드.

단계는 도서 id 매핑 규격 → 주문 수신/중복/보안 → 배송지·수동 배송 → 공급처 입고 순서로 작은 단위로 검증한다. 코드 구현은 별도 후속 작업이며 이번 요청에서는 설계·문서·기존 제출본 업데이트만 진행한다.

학습 수정 과제 **1개**: 위 합성 예시의 도서 id·수량을 바꾼 새 예시를 문서에 직접 추가한다. 실제 개인정보나 인증값은 넣지 않는다.

이해도 질문 **3개**:

1. 쇼핑몰 상품번호가 900이고 ERP 도서 id가 25라면 erp_book_id로 무엇을 보내는가?
2. 같은 외부 주문이 두 번 전송되면 ERP 주문도 두 개 생겨야 하는가?
3. 운영 DB와 개발 DB에서 같은 숫자 id가 나오면 무조건 같은 도서인가?
