# Codex 작업 규칙

## 작업 시작

1. 이 문서와 `PROJECT.md`, `TODO.md`, `DECISIONS.md`를 읽는다. 경로는 저장소 루트의 `doc/` 기준이다.
2. 실제 파일 구조와 Git 상태를 확인하고, 사용자 변경 사항을 보존한다.
3. 요청 범위와 관련된 코드·설정·문서를 확인한다. 문서와 실제 구현이 다르면 차이를 확인하고 함께 정정한다.

## 구현 원칙

- 사용자의 최신 지시를 우선한다. 불확실한 요구사항을 확정된 사실처럼 기록하지 않는다.
- 요청에 필요한 범위로 변경한다. 기술 스택과 업무 범위는 요구사항을 확인한 뒤 결정한다.
- 비밀키, 인증 토큰, 실제 고객 정보와 운영 데이터를 저장소에 넣지 않는다.
- 기존 파일이나 이력을 임의로 삭제하거나 덮어쓰지 않는다. 강제 푸시와 파괴적인 Git 명령을 사용하지 않는다.
- 실행 가능한 코드가 생기면 변경 범위에 적합한 검사·테스트를 실행한다. 실행하지 못한 검사는 이유를 기록한다.
- 문서는 한국어로 작성한다. 명령어와 경로는 실제 환경과 일치하도록 유지한다.

## 필수 학습 모드 — 모든 기능 작업에 적용

이 프로젝트는 취업 포트폴리오이자 Spring Boot 학습 프로젝트다. 개발자는 PHP 웹 개발 경험이 있지만 Java·Spring Boot·JSP 경험은 부족하다. 결과물뿐 아니라 개발자가 면접에서 아키텍처, 코드, SQL, 트랜잭션, 오류 처리를 직접 설명하고 수정할 수 있도록 돕는다.

1. 한 번에 전체 ERP를 개발하지 않는다.
2. 기능을 작게 나누어 하나씩 구현한다. Phase 전체 구현을 기본 작업 단위로 삼지 않는다. 사용자는 완성 코드를 먼저 제공하고 따라가며 배우는 방식을 허용했다. 답을 먼저 제공하지 말아야 한다고 해석하지 않는다.
3. 새 개념이 등장하면 PHP와 비교해서 설명한다. PHP 코드 예시는 개념 비교용인지 실제 프로젝트 코드인지 구분한다.
4. 중요한 코드에는 왜 그렇게 작성했는지 설명한다. 자명한 줄마다 주석을 달기보다 핵심 선택과 책임을 설명한다.
5. 파일별 역할과 요청부터 DB까지의 실행 흐름을 설명한다. DB를 사용하지 않는 요청은 그 사실을 명확히 한다.
6. 기능 구현 후 개발자가 직접 해볼 수정 과제를 정확히 1개 제시한다. 개발자가 요청하기 전에는 그 과제를 대신 수행하지 않는다.
7. 개발자가 이해했다고 명시적으로 확인하기 전에는 다음 기능·단계로 진행하지 않는다. 시간 경과나 응답 없음은 이해 확인이 아니다. 설명, 질문 답변, 현재 기능 오류 해결은 계속 도울 수 있다.
8. 오류가 발생하면 원인과 해결 과정을 먼저 설명한다. 원인이 아직 불명확하면 증상과 확인 방법부터 설명하고 확인된 사실과 추정을 구분한다.
9. 학습 목적에 불필요한 추상화와 복잡한 설계를 피한다.
10. 개발자가 이해하지 못한다고 말하면 더 쉬운 PHP 예제와 작은 입력·출력으로 다시 설명한다.

### 학습 속도 조정 (2026-10-19)

사용자가 진행 속도를 높여 계속하길 요청했다. 기능 하나의 전체 흐름을 먼저 연결해 설명하고, 이미 이해한 문법은 반복하지 않는다. 중간의 단순 확인 질문은 최소화하고 마지막 복습 3개로 이해를 확인한다. 어려움을 표현한 부분만 작은 단위로 나누어 재설명한다. 기능 완료 후 이해 확인 전 다음 기능으로 진행하지 않는 원칙은 유지한다.

### 이번 구현 범위 승인 (2026-10-20)

사용자의 최신 명시 지시인 `phase4 까지 작업`에 따라 이번 작업에서는 Phase 2·3·4의 구현과 검증을 연속해서 진행한다. 중간 학습 답변을 기다리는 규칙보다 이 범위 승인이 우선한다. 기능별 설명은 `PHASE2_4.md`에 남기고 구현 완료와 이해 확인을 구분한다. 이후 학습은 작은 단위로 재개한다. 기존 Docker 배포·서버 호스팅 보류 지시는 유지하며 Dockerfile/Compose 작성과 실제 실행을 구분한다.

각 기능 완료 후 다음 항목을 반드시 제공한다.

- 이번에 만든 기능(기존 기능을 설명한 경우 새 구현과 구분)
- 생성·수정한 파일과 각각의 역할
- 핵심 코드와 작성 이유
- PHP와의 비교
- 실행 방법과 실제 검증 결과(미실행 검사는 명시)
- 직접 해볼 수정 과제 1개
- 이해도 확인 질문 정확히 3개

현재 학습 주제·과제·이해 확인 상태는 `doc/LEARNING.md`에 기록한다. 작업 시작 시 이 파일도 읽는다. 기존 Phase 0·1 구현을 학습 모드 도입 전 완료했다는 사실과 개발자의 이해 여부를 구분한다. 기존 코드도 작은 기능 단위로 설명하고 이해 확인 후 다음 주제로 넘어간다. 이 규칙은 사용자 최신 지시에 따른 필수 작업 방식이며 PRD의 단계별 자동 진행보다 우선한다.

## 문서 관리

- `PROJECT.md`: 목적, 구현 상태, 실제 구조와 기술 스택을 관리한다.
- `TODO.md`: 할 일과 완료 상태를 관리한다. 미완료 작업을 완료로 표시하지 않는다.
- `CHANGELOG.md`: 완료한 변경과 검증 결과를 날짜별로 기록한다.
- `DECISIONS.md`: 중요한 설계 결정, 이유, 영향과 재검토 조건을 기록한다.
- `README.md`: 설치·실행·검증 절차를 관리한다. 아직 없는 실행 명령을 만들지 않는다.
- 작업이 끝나면 반드시 `TODO.md`와 `CHANGELOG.md`를 갱신한다. 구조·설계·실행 방법이 바뀌면 해당 문서도 갱신한다.
- 날짜는 한국 시간(Asia/Seoul) 기준 `YYYY-MM-DD`를 사용한다.

## 사용자 메시지·오류 처리 필수 규칙

[사용자 메시지 가이드](USER_MESSAGES.md)를 따른다. 오류는 ErrorCode와 messages_ko.properties의 한국어 문구로 관리하고 기술적 예외와 분리한다. 사용자를 탓하지 않고 문제와 가능한 다음 행동을 안내하며, 모르는 해결책이나 문의처를 만들지 않는다.

- 로그인 실패는 계정 존재 여부를 노출하지 않는 동일 문구를 사용한다. 로그인·권한 구현 전에는 규격 준비와 실제 적용을 구분한다.
- 검증·중복·업무 규칙·세션·권한·서버 장애를 구분한다. 안전한 일반 입력만 같은 폼에 유지하고 비밀번호·인증정보를 복원하지 않는다.
- JSP 공통 오류 컴포넌트를 사용하고 HTML을 이스케이프한다. SQL·Stack Trace·예외 본문·바인딩 내부 정보는 노출하지 않는다.
- 로그에는 서버 생성 추적 ID와 허용된 코드·예외 종류·정적 위치만 기록한다. 비밀번호, 토큰, 쿠키, SQL 인자, 폼·요청값, 개인정보와 원본 예외 메시지/Throwable은 기록하지 않는다.
- 저장 장애는 반영 여부 확인 후 재시도를 안내한다. 자동 재전송하지 않는다.
- 새 오류 경로는 MockMvc로 계약·입력 보존·비노출을 검증하고 JSP 렌더/XSS는 실제 HTTP로 확인한다.

## 로그인·세션 보안 필수 규칙

[SECURITY.md](SECURITY.md)의 역할 표와 세션/검증 정책을 따른다. Spring Boot가 관리하는 Security 6.5 API를 사용하고 인증·CSRF를 별도 수동 세션 코드로 우회하지 않는다.

- ADMIN/MANAGER/USER 및 직원 객체 권한은 HTTP와 Service에서 검사한다. 공통 도서·거래처에 임의의 소유권을 만들지 않는다.
- 30분 미사용과 8시간 절대 만료를 구분한다. 로그인마다 ID를 교체하고 이전 세션을 폐기한다. 비밀번호/계정 상태 변경은 커밋 후 폐기와 DB 인증 버전 검사를 유지한다.
- DelegatingPasswordEncoder를 사용하고 원문 비밀번호·세션 ID·CSRF 토큰을 로그, MVC 모델, 저장소에 넣지 않는다. 초기 계정은 명시적 bootstrap과 Git 제외 비밀 파일만 사용한다.
- 운영은 Secure/HttpOnly/SameSite·COOKIE만 전달·HTTPS를 유지한다. HTTP 개발 예외를 운영으로 옮기지 않는다.
- CI 워크플로 작성/구문 검사와 GitHub 원격 실행·취약점 스캔 결과를 구분한다. 미실행 검사는 통과로 보고하지 않는다.

## 2026-10-21 — GitHub·배포·지원 준비 요청

사용자가 구현을 마무리하고 GitHub 업로드·서버 호스팅·신입 지원서 작성을 진행하겠다고 요청했다. 검증된 현재 변경을 기존 비공개 저장소에 커밋·푸시하고 CI 결과를 확인하는 범위로 진행한다. 서버는 아직 없고 무료를 우선한다. 호스팅 후보는 실제 무료 조건을 확인해 제안하며 계정 생성·결제·유료 자원 생성은 사용자 동의 없이 수행하지 않는다. 지원 방향은 Spring/JSP/MySQL 신입, 실제 경험은 PHP·Android·iOS 유지보수이며 기간·성과를 추정하지 않는다. 이해 확인 대기와 지원 준비는 구분한다.
